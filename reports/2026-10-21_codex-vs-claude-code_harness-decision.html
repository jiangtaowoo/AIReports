性质：本页是对同日两份韦青式专题报告（2026-10-21_codex.md、2026-10-21_claude-code.md，及 Claude Code 补遗 2026-10-21_claude-code_gap-supplement.md）的对照提炼，不新增事实、不修改原文。两份报告均为条件性判断（置信度均为 medium），引用时须保留其限定。

一、共识：两份报告在同一结论上汇合（可直接进评审基线）

  1. 先分三层，再谈工具：两份报告的首要结论一致——产品、模型、Harness 是三个不同实体，不可混为一谈（Codex 报告 §三 C01；Claude Code 报告 §三 C01）。选型讨论必须先说明谈的是哪一层。
  2. 厂商沙箱/审批层单独不能当硬边界：Codex 报告的表述是“厂商沙箱不能单独当作硬边界”；Claude Code 报告的表述是“审批文本、分类器裁决与仓库配置本身不能作为安全证据”。方向一致，只是落点机制不同。
  3. 仓库配置本身就是信任边界：两份报告独立记载了同一攻击面——恶意仓库的 git/配置在沙箱与审批之外执行。Codex：恶意 .git/config 的 core.fsmonitor 可被后台 git 操作触发，以用户权限执行（§三 C18），另有 .env 重定向 CODEX_HOME + 恶意 MCP 命令的 CVE-2025-61260（§四 C15）。Claude Code：仓库内 Hooks 在信任提示出现前静默执行、MCP 同意可被 enableAllProjectMcpServers 绕过（CVE-2025-59536）、ANTHROPIC_BASE_URL 改写致 API 密钥明文外泄（CVE-2026-21852）（§三 C13、C14；§四 C7）。同一 git 配置攻击面在两份报告中独立出现，是本次对照最值得注意的交叉点。
  4. 审批委托不等于正确性判断：Codex 的自动评审/守护审批可在用户不介入时批准沙箱外命令，失败时把越界执行“合法化”（§四 C14）；Claude Code 的 Auto mode 分类器不是沙箱，审批展示还可被欺骗（SymJack 诱饵路径、GhostApproval 展示与真实目标不一致）（§四 C9、C6）。
  5. 处方收敛到同一组叠加控制：两份报告的门罗五步行动都要求——信任前/加载前审查仓库配置、最小权限、OS 沙箱与网络出口同时生效、高风险动作保留人工复核。Codex 的表述是“加载前评审、委托范围限制、沙箱外执行禁令”；Claude Code 的表述是“信任前人工审查、托管锁定且禁用绕过、已升级修复版本、OS 沙箱与网络出口同时生效”。
  6. 残余风险在两份报告中都未量化：Codex 报告明言“残余风险未量化，不能断言为零”；Claude Code 报告明言满足四项条件“不构成绝对安全证明”。任何一方都不应被写成“已证明安全”。

二、分歧：机制落点不同，部署清单不能互抄

维度 Codex（开源 Harness） Claude Code（闭源 Harness）
证据等级 Harness 有官方博客披露：Agent 主循环、App Server、Item/Turn/Thread 三原语，核心机制多为 supported 内部实现来自社区逆向/第三方解读，报告明确标为 unverified/preliminary，不得当官方架构
沙箱覆盖面 沙箱与审批是两套正交控制：sandbox_mode（read-only / workspace-write / danger-full-access）× approval_policy；workspace-write 默认无出站网络 沙箱仅覆盖 shell 命令，不覆盖文件工具、MCP 服务器与 Hooks；原生 Windows 命令不走沙箱
权限模型 权限画像（beta）与 sandbox_mode 二选一；yolo 类绕过同时移除沙箱与审批 deny/ask/allow 三态，deny 在所有模式（含 bypass）下优先，Hook 的 allow 不能覆盖 deny；PreToolUse Hook 可在工具调用前设卡
企业治理层 内部运行口径：受管网络策略 + 自动评审代批低风险请求 managed-settings.json：托管 deny 可叠加且用户无法移除、可禁用 bypass 模式；CLAUDE.md 禁令只是请求而非保证
信任时序缺陷 项目级配置仅在受信项目加载，但 MCP 命令在配置加载时即可能执行（加载时即信任边界） 更结构性：Hooks/MCP 配置在信任提示出现前就已执行，信任提示本身不是执行边界
标志性逃逸 Heapjack（Desktop node_repl 共享堆窃取令牌，即使 read-only 模式也可执行宿主命令）、Overpatch、DNS 校验前解析泄露（0.163.0 于 2026-10-15 修复）、Windows 命名管道 IPC 接管（CVSS 8.5） worktree .git 沙箱逃逸（CVE-2026-55607，2.1.163 于 2026-06-04 修复）、SneakPeek 桌面预览窗零点击凭据外发（2026-08-17 最终补丁）、GitHub Action checkWritePermissions 未认证写路径（CVSS 4.0 7.8）
成本口径 长会话多次 compaction 重复计费、自动 compaction 约 5 分钟、长任务 30 分钟膨胀至 3 小时（社区投诉口径） 5 小时滚动窗口 + 周限额（周限额不公布绝对值，只公布倍数）；2026-09-14 起周限额相对基线永久 +25%，相对临时峰值约 −17%；并行约 10 倍消耗（第三方口径，须实测）
中国区 报告 §六聚焦采用率与渠道（Stack Overflow 2026 调查口径：挑战者而非领导者），未给出中国区定价/合规结论 补遗结论：官方不支持中国内地/香港/澳门（台湾在列），无中国区定价与本地部署；中转代理不应进入企业选型基线

三、给技术评审的统一部署清单（两份报告门罗五步的交集）

  1. 不可信仓库一律先隔离审查再谈信任：静态检查 .git/config、config.toml/mcp_servers、.claude/、.mcp.json、Hooks 与 ANTHROPIC_BASE_URL 类重定向项；审查完成前不在主环境打开或执行该仓库。
  2. 版本下限以官方 advisory 为准，当前可执行的部分下限：Codex ≥ 0.163.0（DNS 修复，2026-10-15）；Claude Code ≥ 2.1.247（Beltdown 完整修复，2026-08-26）并单独确认桌面端 SneakPeek 2026-08-17 补丁已应用。Heapjack/Overpatch 的修复版本号在 Codex 账本中未给出（仅称 2026-09-15 公开后约 8 日内修复），须另行核对。
  3. 沙箱与网络出口逐项实测，不以档位名称或审批通过作为证据：越境写与非预批域名访问测试须为零成功；Codex 侧核对 workspace-write 默认断网与受保护路径只读；Claude Code 侧核对沙箱不覆盖文件工具/MCP/Hooks 这一缺口。
  4. 审批委托书面划界：仅限低风险/已充分授权范围代批，高风险动作一律人工复核；Claude Code 侧禁用 bypass 模式并以托管 deny 锁定基线。
  5. 成本按实测预算，不按倍数口头换算：Claude Code 的 Max 20x 是“每会话倍数”而非月度 20 倍；Codex 的长会话 compaction 成本逐次记录。

四、仍未闭合，引用时必须保留的限定

  • Claude Code 报告内 2.0.65 的归属不一致：§三称 CVE-2025-59536 在 2.0.65+ 修复，§四行动项称 2.0.65 覆盖 CVE-2026-21852。补遗亦说明两起 CVE 的官方 advisory 原文均未核实。部署核查时应以官方 advisory 为准，不要直接引用报告中任一处归属。

  • Claude Code 云端写路径不在放行范围：报告 §四明言云端写路径因细节未核对，不在放行范围内；GitHub Action 与 bash validator 绕过的官方 advisory 细节、适用版本与修复状态未核对。
